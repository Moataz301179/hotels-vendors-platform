## Local guardrails applied in this continuation

- **Integrations:** new `lib/integrations/admin-route.ts` applies existing authentication, `admin:manage_platform`, and API rate limiting to provider, sync, budget, three-way match, and webhook API routes.
- **Agents:** `/api/v1/agents/run` now requires platform permission, rejects malformed/ambiguous inputs, limits custom prompt size, rate-limits execution, scopes feature proposals to the caller tenant, and records the run.
- **Lead data:** lead retrieval is permission-gated and audited; public lead-capture logs no longer include company/email or raw database error messages.
- **Shipments:** GET authenticates and returns only rows owned by the authenticated buyer. Persistence/tenant linkage for writes is still required.
- **Onboarding read:** initial progress GET is side-effect free instead of creating database state.

These are local source changes only. They do not settle the shared Clerk/JWT architecture or make the product production-ready.

## “What could go wrong” acceptance suite

Run as integration tests against isolated fixtures before release. These are required controls, not all executed in this source audit.

1. **Identity:** anonymous/expired/disabled user denied; verified mobile and web sessions reach the same intended identity; unverified email and duplicate-account collisions cannot silently link; refresh replay/revocation and logout are enforced.
2. **Tenant/RBAC:** tenant A cannot read, mutate, export, or infer tenant B records through IDs, nested relations, filters, headers, bulk actions, agents, or file URLs; non-admin denied from platform tools.
3. **Orders/checkout:** invalid transitions and missing payment/authority fail; parallel requests yield one transition; tenant ownership is rechecked under lock; invoice, credit, order, and audit all commit or all roll back; retries return one result.
4. **GRN/inventory/credit note:** wrong order/item/invoice, over-receipt, negative quantity, duplicate scan, invalid transition, insufficient outstanding credit, and cross-tenant references fail; accepted/rejected totals reconcile atomically.
5. **POD/shipping/ETA:** absent proof, local file URI, wrong stop, unauthorized actor, bad signature, stale/replayed event, and mismatched trip fail; valid capture persists recipient, notes, durable proof reference, actor, and timestamps exactly once.
6. **Money/webhooks/factoring:** invalid signature, missing event ID, old timestamp, wrong currency/amount/reference, duplicate and concurrent callback, Redis outage, and injected mid-transaction failure cannot double-pay or release credit early.
7. **Onboarding/compliance:** client-supplied booleans cannot grant KYC/credit approval; reviewer/evidence state controls completion; read requests have no DB writes.
8. **Integrations/queues:** unsupported or stub connector never says connected/success; unauthorized sync denied; signed inbound event is tenant-mapped and deduplicated; retry/DLQ preserves exactly-once business effects.
9. **AI/agents/logging:** only allowlisted workflows execute; prompt size/cost limits hold; tenant data does not cross in output; secrets/PII are absent from logs; audit write failure blocks protected financial or privilege-changing actions.
10. **Mobile/UI/metrics:** server/client request schemas stay compatible; upload failure blocks POD submit; offline and refresh races do not show false success; error/unknown/empty states are distinct; zero denominator never reports 100%.
11. **Release/data:** schema and generated client agree; migration rollback and data restore are rehearsed; pending migrations are explicit; queue recovery and application rollback are verified before deployment.

## Release disposition

Not ready for production sign-off. The highest priority unresolved items are identity/session reconciliation, payment callback atomicity and amount verification, canonical order/GRN transition controls, POD evidence contract, durable tenant-scoped shipment persistence, onboarding evidence-based approval, and passing type/lint/release gates.

The broad Clerk conversion remains blocked by automatic review because it changes the authentication boundary and account-linking behavior across protected APIs. The two viable decisions are: make Clerk canonical and migrate mobile/shared APIs to that session contract, or retain JWT as canonical and adapt web authentication to issue/refresh that session. Explicitly choose before touching shared authentication or account linking.
