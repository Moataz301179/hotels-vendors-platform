# HotelsVendors cumulative recovery harness

`pending-tasks.json` is the durable, append-only task inventory for prior attempts and newly discovered issues. Do not remove an unfinished task or mark it verified without reproducible evidence. Add new findings with a unique ID and state `pending`.

`node scripts/recovery-gate.mjs` validates task identities and evidence and writes `recovery-reports/latest.json`. `node scripts/recovery-gate.mjs --require-ready` fails until every task has verified evidence. The release manifest remains the canonical task inventory.

The GitHub Recovery Harness runs on matching pull requests, manual dispatch, every six hours, and immediately after completed CI, parallel engineering diagnostics, or browser E2E workflows. Its incident router reads workflow/job/check metadata only; it does not download logs or execute source from the triggering branch. Reports bind evidence to the exact 40-character candidate SHA, classify failed jobs to existing P0/P1 tasks, and include a next gate. CI/database tasks are reported `verified_for_sha` only when every named required check is green for that same SHA. Evidence for an older or different SHA cannot advance the candidate phase.

The router requests at most one targeted GitHub rerun for a same-repository job that timed out on its first attempt. Deterministic test/build failures are routed to repair without blind retries. A passing run advances only the run's evidence phase; it never changes `pending-tasks.json` or marks external/manual acceptance complete. The canonical task state stays pending until its required evidence is recorded.

The local repair worker is an opt-in extension of `scripts/recovery/repair-controller.py`. Run it as a managed foreground process (for example, under the host's approved `launchd`/`systemd` service) with `HV_REPAIR_EXECUTOR=codex-chatgpt HV_REPAIR_CODEX_BIN=/absolute/path/to/codex HV_REPAIR_PUBLISH_BRANCH=release/nov02-verified python3 scripts/recovery/repair-controller.py --watch-repairs --interval 900 --poll-seconds 300`. It runs the inventory controller every 15 minutes and polls GitHub's public REST API at least every five minutes for completed allowlisted workflow runs on exactly `release/nov02-verified`. It requests branch/run/job/check metadata only, never raw logs, and uses no GitHub token. Failed incidents route directly to repair; no manual inbox handoff is required. The one-shot local-only alternative is `HV_REPAIR_EXECUTOR=codex-chatgpt node scripts/recovery/repair-loop.mjs --repo /absolute/path/to/repo --incident /path/to/incident.json`.

For each supported task (`P0-CI`, `P0-DB`, `P0-LIFECYCLE`, `P0-UX`), the worker verifies the full source SHA, same-repository workflow evidence, canonical origin, and exact current candidate-branch head. It performs a read-only ChatGPT Codex transport preflight, fetches the candidate commit if needed, creates a dedicated Git worktree at that SHA, and runs `npm ci --legacy-peer-deps` from the tracked lockfile inside that worktree only. Codex gets workspace-write access only in that isolated worktree, via stdin with EOF, a sanitized environment, no paid API-key fallback, and a process-group timeout. It is limited to two attempts, with a persisted 15-minute circuit breaker on auth/transport timeout. The outer harness checks protected paths and local gates before committing. With the explicit publish target set, it rechecks canonical origin and exact remote base SHA before a normal, non-force fast-forward push to `release/nov02-verified`; any mismatch/rejected push blocks. After a successful push it waits for CI on that new exact SHA before choosing the next phase. The canonical task manifest remains pending and production readiness remains false.

The default supported phase order is `P0-CI` → `P0-DB` → `P0-LIFECYCLE` → `P0-UX`. One task is repaired per incident and a new same-SHA workflow event is needed before selecting the next task. Tasks that require manual role, Neon, catalog, mobile, reconciliation, or production approval remain with their acceptance processes. The worker has not been demonstrated on the official Mac runner yet: Codex transport diagnostics report an invalidated ChatGPT refresh session (`401`/`token_revoked`). It stops on auth errors and keeps the incident eligible for retry after its persisted 15-minute breaker expires, so the managed poller resumes after reauthentication. Until the worker completes a real isolated repair and local gates, treat the executor as blocked. It does not read workflow logs, operate on production databases, mutate task state, merge, migrate, or deploy. Candidate source publication requires the explicit target variable above; production Neon restore/migrations, secrets, user/vendor data, destructive changes, merge, and deployment remain approval-gated. The recovery workflow does not dispatch or modify production.
